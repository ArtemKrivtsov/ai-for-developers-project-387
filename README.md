# Календарь звонков (продолжение)

[![hexlet-check](https://github.com/ArtemKrivtsov/ai-for-developers-project-387/actions/workflows/hexlet-check.yml/badge.svg)](https://github.com/ArtemKrivtsov/ai-for-developers-project-387/actions)

Интегрируйте работу агентов в GitHub проект

Приложение «Календарь звонков» перенесено из первого проекта, [ai-for-developers-project-386](https://github.com/ArtemKrivtsov/ai-for-developers-project-386). Здесь вокруг него автоматизируется процесс разработки в GitHub: разбор задач, реализация, ревью и регулярные проверки выполняют агенты в Actions, решения остаются за человеком.

**Приложение:** https://ai-for-developers-project-386-cehm.onrender.com

Учебный проект Хекслета: https://ru.hexlet.io/programs/ai-for-developers
Как это должно работать: https://files.hexlet.app/a/2ipc5m

## Сценарий

Упрощённый аналог [Cal.com](https://cal.com/). Владелец календаря один и задан заранее, гость записывается без регистрации.

1. Владелец на своей странице создаёт тип встречи: название, описание и длительность, например «Знакомство», 30 минут.
2. Гость открывает главную страницу, переходит в каталог типов встреч и выбирает нужный.
3. Открывается календарь на ближайшие 14 дней. Гость выбирает день и видит свободные слоты. Слот длится столько же, сколько выбранный тип встречи, занятое время не предлагается.
4. Гость выбирает слот, вводит имя, email и при желании тему разговора — короткий текст до 500 символов — и записывается.
5. Сервер проверяет, что время всё ещё свободно, и создаёт встречу. Если слот успели занять, гость получает ошибку и выбирает другое время.
6. Владелец открывает список предстоящих встреч и видит новую встречу: тип встречи, дату и время, имя и email гостя. Если гость указал тему разговора, она видна под именем и email. В списке встречи всех типов.

### Правила

- Окно записи занимает 14 календарных дней и сдвигается каждый день.
- Встречи не пересекаются даже частично, в том числе встречи разных типов. Следующая встреча может начаться в момент окончания предыдущей.
- Правило действует и для одновременных запросов на одно время: встреча появится только одна.
- Первый день окна, часы работы владельца, часовой пояс и шаг стартов слотов фиксируются в спецификации.

### Ограничения

- Нет авторизации, личных кабинетов, внешних календарей и уведомлений.
- API описан контрактом на TypeSpec. Из него генерируются OpenAPI-спецификация и клиентский SDK для фронтенда.
- Приложение собирается в Docker-образ и запускается в контейнере.

## Стек

- Контракт API: TypeSpec → OpenAPI 3.0.
- Бэкенд: Node.js 26, Fastify, fastify-openapi-glue, типы маршрутов генерирует hey-api.
- Фронтенд: React, Vite, Mantine, React Router, SDK генерирует hey-api.
- Тесты: Vitest, во фронтенде Testing Library и jsdom, сквозной сценарий на Playwright в Chromium. Линтеры: oxlint, oxfmt, jactionlint, tsc.
- Окружение: mise (инструменты, задачи, фоновые процессы), hk (git-хуки), pnpm workspaces.

## Установка

Нужен [mise](https://mise.jdx.dev/getting-started.html), остальные инструменты он поставит сам. Для `mise run check` нужен ещё запущенный [Docker](https://docs.docker.com/get-started/get-docker/): проверки собирают образ приложения и запускают контейнер.

```bash
git clone https://github.com/ArtemKrivtsov/ai-for-developers-project-387.git
cd ai-for-developers-project-387
mise trust && mise install
mise run setup
```

`mise run setup` ставит и Chromium для браузерных тестов. На Linux браузеру нужны ещё системные библиотеки: `pnpm --dir e2e exec playwright install-deps chromium`, команда просит sudo.

Для работы с агентом нужен набор скиллов [mattpocock/skills](https://github.com/mattpocock/skills), он ставится глобально. Настройка под репозиторий уже лежит в `docs/agents/`.

```bash
npx skills@latest add mattpocock/skills -g
```

## Использование

```bash
mise daemons start   # бэкенд на :3000, фронтенд на http://localhost:5173
mise daemons stop
mise run check       # все проверки, те же, что в CI
```

Как вызвать: написать в issue или PR комментарий с командой, например `/oc explain this issue` или `/oc запусти скилл to-spec по обсуждению этого issue`.

### Примеры команд

Команда должна быть в тексте комментария, регистр не важен.

```bash
/oc разбери этот issue: что нужно сделать и какие файлы затронуты
/oc запусти скилл to-spec по обсуждению этого issue
/oc запусти скилл to-tickets по спецификации из этого issue
/oc запусти скилл implement-spec по тикетам из этого issue
```

- `to-spec` собирает обсуждение в спецификацию и публикует её в трекере.
- `to-tickets` режет спецификацию на тикеты с зависимостями.
- `implement-spec` реализует тикеты по плану.

Правка по коду идёт из PR: откройте **Files changed**, оставьте комментарий к нужной строке diff с командой, например:

```bash
/oc исправь: здесь не учтён часовой пояс гостя
```

Агент прочитает diff и контекст PR, внесёт правку в ветку и ответит в ветке этого комментария.

### Автотриаж новых обращений

Воркфлоу `opencode-triage.yml` запускается, когда открыто новое issue, и разбирает его без команды `/oc`. Инструкция для агента лежит в `prompt` воркфлоу: прочитать `AGENTS.md` и `docs/agents/`, проверить, что приложение уже умеет, задать вопросы и поставить метку `needs-info` или `needs-triage`. Код агент не меняет, issue не закрывает, метки `ready-for-*` не ставит: решение, брать ли задачу, за человеком.

- **Кого разбирает:** только issue от владельца, участников и коллабораторов, не от ботов.
- **Кого пропускает:** тикеты, которые уже подготовлены скиллами `to-spec` и `to-tickets`. Их отличают метки из `docs/agents/triage-labels.md`: `ready-for-agent`, `ready-for-human` и `wayfinder:*`. Тикеты, которые агент создаёт сам из Actions, пропускаются ещё и фильтром ботов.
- **Права, модель, скиллы, `share` и запрет запросов разрешений** такие же, как у `opencode.yml`. Тайм-аут 20 минут, по каждому issue один прогон.

Агент в Actions не может менять файлы в `.github/workflows/`: у приложения `opencode-agent` нет права `workflows`, и GitHub отклоняет такой push. Воркфлоу правит человек или локальный агент.

### Авторевью pull request

Воркфлоу `opencode-review.yml` запускается на каждый PR и на каждый новый push в него. Это отдельный запуск OpenCode CLI: он не продолжает сессию реализации и не правит код. Ревьюер читает [`REVIEW.md`](REVIEW.md), описание PR, исходное обращение, спецификацию и согласование по ссылкам, diff между базой и head и результаты CI. Критерии берутся из `REVIEW.md` базовой ветки, чтобы PR не ослабил правила собственного ревью. Отчёт агент пишет в файл, задание без отчёта падает. Публикует отчёт отдельное задание `publish` командой `gh pr comment`: у него есть право записи, но нет ключа модели.

- **Права токена раннера:** у задания с моделью только чтение: `contents`, `issues`, `pull-requests`, `actions`, `checks` и `statuses`. Писать в PR оно не может, даже если модель попытается. `pull-requests: write` есть только у задания `publish`, где модели нет. Обмен через OIDC не нужен.
- **Права агента:** правка файлов запрещена, кроме его отчёта `.review/review.md`. Из команд разрешены только читающие `git diff/log/show` и `gh pr view/diff/checks`, `gh issue view`, `gh run list/view`, причём без `--output` и перенаправления `>`: так эти команды тоже пишут файлы. Сеть и пути вне checkout запрещены. Настройки OpenCode не считаются границей безопасности, граница — права токена.
- **Кого ревьюит:** PR из веток этого репозитория от владельца, участников и коллабораторов, а также PR самого агента `opencode-agent[bot]`. Общий фильтр ботов здесь не подходит: он отключил бы ревью работы агента. PR из fork не получают ни ревью, ни ключа модели, `pull_request_target` не используется.
- **Тайм-аут** 20 минут. Новый push отменяет устаревшее ревью того же PR (`cancel-in-progress: true`).
- Комментарий авторевью сам ничего не исправляет. Человек разбирает замечания и передаёт подтверждённые агенту командой `/oc` в PR.
- **Ключ и изменённый воркфлоу.** Воркфлоу на `pull_request` берётся из head PR. Участник с правом записи может изменить его в своей ветке и получить ключ модели, но то же право и так даёт ему секреты через любой воркфлоу на `push`. Граница доверия — список коллабораторов. PR из fork ключ не получают.

### Предел запусков на PR

Перед вызовом модели первый шаг задания `agent #N` в `opencode.yml` считает, сколько раз агент уже запускался на этом PR. Шаг идёт внутри группы `concurrency` агента, поэтому две одновременные команды не проходят проверку обе. Учитывается каждое прежнее задание `agent #N`, которое стартовало, с любым исходом: успех, ошибка, отмена, тайм-аут и прошлые попытки Re-run. Счётчик берётся из истории Actions, которую токен приложения агента переписать не может. Комментарии PR служат только отчётом и на бюджет не влияют. Предел — 3 запуска на PR. Новый PR получает новый бюджет, у обычных issue предела нет.

Если агент не ответил, задание `report` без вызова модели публикует в PR причину, последний SHA и ссылку на логи со статусом «нужен человек»:

| Причина           | Когда                                                                            |
| ----------------- | -------------------------------------------------------------------------------- |
| `limit_exhausted` | бюджет PR исчерпан, модель не вызывалась                                         |
| `timeout`         | агент не уложился в 45 минут                                                     |
| `infra`           | сбой подготовки: проверка бюджета, checkout, установка скиллов, нет ключа модели |
| `agent_failed`    | агент завершился с ошибкой или прогон отменили, причину проверить по логам       |
| `fork`            | команда в PR из fork, агент не запускался                                        |

Предел держится, пока сохранена история Actions и не изменён воркфлоу: администратор репозитория может изменить и то, и другое.

### Браузерная проверка PR

`pr-e2e.yml` запускает браузерные сценарии из `e2e/` на точном head SHA PR (`github.event.pull_request.head.sha`), а не на временном merge-коммите. Фактический `git rev-parse HEAD` сверяется с head и записывается в артефакт `e2e-<sha>` вместе с результатом, trace и отчётом Playwright. Перед мержем человек сверяет SHA артефакта с текущим head PR. После нового push проверка повторяется, старый артефакт остаётся свидетельством прежней версии.

### Шаблон PR и защита `main`

Описание PR заполняется по [шаблону](.github/pull_request_template.md): связи с обращением, спецификацией, тикетами и согласованием, проверки с командами, прогонами и SHA, риск и способ отката. Мерж в `main` возможен только после успешного `check`, это требует защита ветки.

### Регулярный аудит

Воркфлоу [`audit.yml`](.github/workflows/audit.yml) раз в сутки, в 06:17 по Москве (`schedule` с `timezone: Europe/Moscow`), проверяет развёрнутое приложение. Его можно запустить и вручную: Actions → audit → Run workflow (`workflow_dispatch`). Режим `live` проверяет адрес из переменной репозитория `APP_URL`, режим `training` берёт подготовленный учебный отчёт `audit/fixtures/training-report.json` с известной находкой.

1. **Сбор данных без модели.** Задание `collect` будит приложение на Render, запускает Lighthouse и сводит отчёт скриптом `audit/summarize.mjs`. В находки попадают проверки из четырёх основных категорий с ненулевым весом и оценкой ниже 90, у каждой есть стабильный отпечаток вида `lighthouse:<audit-id>`. Если приложение не ответило, отчёт так и говорит: «нет данных», а не «находок нет». Полный отчёт (JSON и HTML) и сводка сохраняются артефактом `audit-report-<run_id>` на 90 дней. Отчёты лежат вне рабочего дерева, а `.audit/` в `.gitignore`, поэтому в коммиты они не попадают.
2. **Разбор агентом.** Задание `agent` запускает OpenCode CLI с инструкцией в `prompt`. Для каждой находки агент ищет задачу с тем же отпечатком (`gh issue list --label audit --search`). Если открытая задача уже есть, он ничего не создаёт. Если задачи нет, он заводит одну issue с метками `audit` и `needs-triage`: проблема, проверенное приложение, предлагаемое действие, ссылка на прогон и отпечаток. Если задача была закрыта, агент заводит новую со ссылкой на прежнюю. Учебные находки получают метку `учебный` и префикс `[Учебный]`.
3. **Вывод.** Агент записывает итог в файл, а задание `journal` без модели публикует его комментарием в [журнал аудита #18](https://github.com/ArtemKrivtsov/ai-for-developers-project-387/issues/18) со ссылкой на прогон. Задание запускается всегда: если сбор или агент упали, в журнал попадает «без вывода агента: нужен человек». Так ни один запуск не остаётся без записи, а вывод не пропадает вместе с артефактом.

- **Права:** у `collect` только `contents: read`. У `agent` `contents: read` и `issues: write` для токена раннера: агент создаёт issue, код и PR не трогает, поэтому `contents: write` и OIDC ему не нужны. Из команд агенту разрешены только `gh issue list/view/create` и `gh label list`, без `--output` и перенаправления. Писать он может только файл своего вывода. У `journal` без модели `actions: read` и `issues: write` для комментария в журнале. Права согласованы в [#19](https://github.com/ArtemKrivtsov/ai-for-developers-project-387/issues/19).
- **Ограничения:** расписание срабатывает раз в сутки, ручные запуски не ограничены числом. `concurrency: audit` пускает по одному аудиту за раз, остальные ждут. Тайм-ауты: `collect` 15 минут, `agent` 20, `journal` 5.
- **Когда ждать запуск:** расписание работает, только пока файл лежит в `main` и воркфлоу включён. GitHub может задержать или пропустить запуск по расписанию, а в публичном репозитории отключает его после 60 дней без активности. Проверять сценарий можно ручным запуском.
- Найденная задача остаётся входящим обращением: брать ли её в работу, решает человек, дальше применяется цепочка `to-spec` → `to-tickets` → `implement-spec`.

### Настройки воркфлоу

- **Команды (`mentions`):** набор по умолчанию, `/oc` и `/opencode`. В воркфлоу он записан явно.
- **Публикация сессий (`share`):** выключена. Репозиторий публичный, а для публичных репозиториев OpenCode по умолчанию публикует сессию со всем контекстом задачи.
- **Модель:** бесплатная модель [OpenCode Zen](https://opencode.ai/docs/zen/), карта и бюджет не нужны. Ключ лежит в секрете `OPENCODE_API_KEY`. Бесплатные модели Zen временные: если модель уберут, в `model` ставится другая из списка Zen.
- **Авторизация:** стандартная, через [OpenCode GitHub App](https://github.com/apps/opencode-agent), установленное на репозиторий. Задание агента получает `contents: read` и `id-token: write`, по OIDC обменивает их на токен приложения; checkout идёт с `persist-credentials: false`. Комментирует и пушит агент правами приложения. Для бюджета задание агента читает историю Actions (`actions: read`) и head-репозиторий PR (`pull-requests: read`). Задание `report` без модели получает `contents: read`, `actions: read`, `issues: write` и `pull-requests: write` только для комментария с причиной. Права авторевью описаны выше. Согласование прав: [#15](https://github.com/ArtemKrivtsov/ai-for-developers-project-387/issues/15#issuecomment-6878079348).
- **Кто может вызвать:** только владелец, член организации и коллаборатор репозитория. Комментарии ботов пропускаются, чтобы агент не отвечал сам себе. PR из fork агент не обрабатывает: комментарий к строке diff не запускает задание, а комментарий в обсуждении такого PR останавливается проверкой до checkout, поэтому ключ модели к чужому коду не попадает.
- **Без запросов разрешений:** на раннере некому отвечать на запросы OpenCode, а правило `ask` подвешивает прогон до тайм-аута. Поэтому в `OPENCODE_CONFIG_CONTENT` вне репозитория разрешены только папка скиллов `~/.agents/skills` и `/tmp`, остальное запрещено. Чтение `.env` и повтор одного и того же вызова (`doom_loop`) тоже запрещены. Заголовок сессии генерирует та же бесплатная модель (`small_model`).
- **Ограничения:** тайм-аут агента 45 минут, его хватает на `implement-spec`. По каждому issue или PR одновременно идёт один прогон, следующая команда ждёт его окончания. На PR действует предел запусков, см. выше.
- **Скиллы:** раннер начинает с чистого окружения, поэтому воркфлоу ставит набор [mattpocock/skills](https://github.com/mattpocock/skills) глобально, как на машине разработчика. Версии закреплены: CLI `skills@1.8.1` и коммит набора. Настройки трекера в `docs/agents/` и правила в `AGENTS.md` приходят вместе с кодом.
- **Как остановить:** Actions → прогон → Cancel workflow останавливает текущий прогон, Actions → opencode → Disable workflow отключает будущие. Ключ можно отозвать в кабинете OpenCode Zen.

### Где смотреть результат

Ответ агента — комментарий приложения `opencode-agent` в том же issue или PR. На команду в строке diff ответ приходит в ветке этого комментария.

Прогон — вкладка [Actions](https://github.com/ArtemKrivtsov/ai-for-developers-project-387/actions/workflows/opencode.yml) → workflow `opencode` → нужный запуск. Ссылку на прогон агент добавляет в конец ответа (`github run`). В логе видны шаги `Install agent skills` и `Run opencode`, включая ввод и вывод. Если прогона нет, проверьте, что комментарий оставил владелец, член организации или коллаборатор и в нём есть `/oc` или `/opencode`.

## Выводы о работе GitHub-агента

Что получилось за проект: агент OpenCode в Actions провёл доработку «Тема разговора» от жалобы пользователя ([#5](https://github.com/ArtemKrivtsov/ai-for-developers-project-387/issues/5)) через разбор, спецификацию [#7](https://github.com/ArtemKrivtsov/ai-for-developers-project-387/issues/7) и тикеты [#8](https://github.com/ArtemKrivtsov/ai-for-developers-project-387/issues/8), [#9](https://github.com/ArtemKrivtsov/ai-for-developers-project-387/issues/9) до PR [#17](https://github.com/ArtemKrivtsov/ai-for-developers-project-387/pull/17). Новые обращения разбирает автотриаж, каждый PR проверяет независимое авторевью, раз в сутки аудит Lighthouse заводит задачи по находкам.

**Что потребовало уточнений и что пришлось изменить:**

- **Агент на раннере зависал молча.** Первый `to-spec` 12 минут ждал разрешения на чтение файла вне репозитория (`external_directory: ask`), которое в Actions дать некому. Пришлось явно описать права OpenCode в `OPENCODE_CONFIG_CONTENT`: разрешить нужные пути, остальное запретить вместо `ask`. Тот же урок: модель для заголовков сессии по умолчанию платная и падала с 402, её тоже пришлось задать явно.
- **Права агента не граница безопасности.** Ревьюеру запретили писать файлы, а он записал отчёт через `git log --output`. Правило на `/tmp/review/*` просто не срабатывало, и это видно только по логу, а не по результату. Границей стали права токена раннера: задание с моделью только читает, публикует отдельное задание без ключа.
- **Агент не может менять воркфлоу.** У приложения `opencode-agent` нет права `workflows`, поэтому GitHub отклонил его push с автотриажем. Все воркфлоу писал локальный агент, а агенту в Actions остались код, документация и issue. Я считаю это правильной границей, а не помехой.
- **Формат ответа агента не равен формату PR.** OpenCode взял заголовок и описание PR из итогового сообщения агента: заголовок вышел не по Conventional Commits, шаблон оказался внутри блока кода. Исправлять пришлось отдельной командой `/oc`, а в инструкциях теперь явно сказано, как оформить PR.
- **Авторевью полезнее, чем я ожидал.** Оно нашло настоящие дефекты: имя задания `agent #N` без кавычек YAML обрезал до `agent`, и бюджет никогда не срабатывал. Ещё оно нашло гонку двух команд за бюджет, счётчик символов, который расходился с проверкой формы, и сбой сбора, после которого журнал оставался пустым. Одно его замечание я сначала зря отклонил и потом исправил это публично. Обратная сторона: ревью каждый раз находит что-то в описании PR, и цикл правок нужно останавливать решением человека.
- **Тесты как защита.** Найденный класс ошибок закрывали проверками: шаг `workflow-names` ловит `#` в имени задания, API-тест закрепляет счёт лимита по символам, а не по UTF-16, тесты сводки аудита ловят сдвиг порога. Каждую проверку я сначала показал падающей на сломанной версии.
- **Бесплатная модель справилась.** `deepseek-v4.1-flash-free` выполнила `implement-spec` примерно за 17 минут с тестами на всех уровнях. Медленно, но для учебного проекта карта и бюджет не понадобились.

**Что я бы сделал иначе:** сразу описывать права агента в конфиге и проверять их по логу первого прогона. Предел запусков и задания отчёта без модели закладывать до первого PR, а не после. И заранее договориться, сколько кругов авторевью допустимо до решения человека.

## Деплой

Приложение опубликовано на Render: https://ai-for-developers-project-386-cehm.onrender.com

Render собирает образ по `Dockerfile` из ветки `main` репозитория первого проекта, [ai-for-developers-project-386](https://github.com/ArtemKrivtsov/ai-for-developers-project-386), и передаёт порт в переменной `PORT`. Если адрес недоступен, приложение запускается локально командой `mise daemons start` из раздела «Использование» или в Docker:

```bash
docker build -t calendar .
docker run --rm -p 8080:8080 calendar   # http://localhost:8080
```

Типы встреч и встречи хранятся в памяти сервера и пропадают при каждом перезапуске: после деплоя, рестарта и засыпания сервиса. Бесплатный сервис Render засыпает после 15 минут без запросов. Первый запрос после этого ждёт запуска около минуты, и в календаре остаются только два стартовых типа встреч.

### MCP-сервер Render

Выкатом управляет агент через [MCP-сервер Render](https://render.com/docs/mcp-server). Для Claude Code сервер описан в `.mcp.json`, API-ключ берётся из переменной окружения `RENDER_API_KEY`.

1. Создайте API-ключ в Render: [Account Settings → API Keys](https://dashboard.render.com/u/settings?add-api-key).
2. Сохраните его в `.env.local` строкой `RENDER_API_KEY=<ключ>`. Файл в `.gitignore`, в репозиторий ключ не попадёт.
3. Запустите агента с этой переменной:

   ```bash
   set -a; . ./.env.local; set +a
   claude
   ```

4. При первом запуске подтвердите сервер `render` из `.mcp.json`. В `claude mcp list` у него должно стоять `Connected`.
