# Критерии ревью календаря

Файл читает независимый ревьюер: воркфлоу `opencode-review.yml` передаёт его агенту в запросе на каждый pull request. Человек пользуется теми же критериями перед мержем.

## Что проверяет ревью

1. **Соответствие задаче.** PR делает то, что согласовано в спецификации и тикетах, на которые он ссылается, и не больше. Ссылки на исходное обращение, спецификацию, тикеты и комментарий согласования есть в описании PR и открываются. Если ссылки нет или изменение выходит за согласованный объём, это замечание.
2. **Запись и занятое время.** Занятый слот не должен оставаться доступным для повторной записи. Встречи не пересекаются даже частично, в том числе встречи разных типов, и одновременные запросы на одно время создают одну встречу. Встреча может начаться в момент окончания предыдущей. Окно записи 14 дней, рабочие часы и часовой пояс из спецификации не меняются без отдельного решения.
3. **Контракт API.** Изменение API начинается с `spec/main.tsp` и проходит через `mise run generate`. Файлы в папках `generated/` руками не правятся. Новое поле одинаково описано в контракте, обработчике, хранилище и клиенте. Ошибки валидации называют поле (`field`), по которому клиент покажет ошибку.
4. **Данные гостя.** Всё, что ввёл гость, проверяется на сервере, а не только в форме: длина, пустые значения, пробелы по краям. Сервер не доверяет клиенту в правилах записи.
5. **Соседнее поведение.** Сценарии, которые спецификация требует сохранить, работают как раньше и покрыты тестами, которые проходили до изменения.
6. **Тесты.** Основной и негативный сценарии спецификации покрыты тестами на том уровне, где живёт правило: API, компонент или браузер. Тест проверяет внешнее поведение, а не внутреннюю структуру. Тест, который проходит и без реализации, не считается.
7. **Риск и откат.** Разделы шаблона PR о проверках, риске и откате заполнены для этого изменения. Глубина проверки соответствует последствиям ошибки, а не числу строк.
8. **Права и секреты.** Изменение в `.github/workflows/` не расширяет права токена, не отдаёт секреты коду из fork и не снимает фильтры доверенных авторов. Такое изменение требует отдельного решения человека, ревью его явно отмечает.
9. **Сообщения коммитов** следуют Conventional Commits, коммит реализации ссылается на тикет.

## Как писать замечание

- Каждое замечание указывает файл и строку, условие, при котором возникает ошибка, и её последствие для гостя или владельца.
- Замечание о дефекте отличается от предложения: предложение помечается словом «Предложение» и мерж не блокирует.
- Форматирование и стиль проверяют линтеры. Их вывод в ревью не повторяется.
- Если подтверждённых дефектов нет, ревью прямо пишет: «Подтверждённых дефектов не найдено». Придумывать замечания не нужно.
- Повторное ревью учитывает уже разобранные замечания из обсуждения PR и проверяет новые правки и затронутое ими поведение.

## Уроки прошлых ревью

Сюда добавляются правила, которые закрывают найденный класс ошибок, если защиту нельзя выразить тестом или правилом линтера.
